# 提交前密钥卫生检查

## 何时使用
- 准备 `git commit` / `git push`，或把私有仓库改为公开开源之前
- 新增了调用 LLM API、数据库或其他第三方云服务的代码
- 用户怀疑密钥、令牌或 `.env` 配置已经泄露

## 检查步骤
1. **确认工具**：运行 `gitleaks version`；未安装时提示用户按官方 README 安装（如 `brew install gitleaks` 或官方 Release），不要下载来路不明的二进制文件。
2. **扫描当前工作区文件**：运行 `gitleaks dir -v .`，排查未提交及当前目录中的敏感凭证与误跟踪文件。
3. **扫描 Git 提交历史**：运行 `gitleaks git -v .`（历史提交中出现过的密钥即使已在最新代码删除，同样视为已泄露）。
4. **检查环境变量与忽略配置**：
   - 核查 `.gitignore` 是否包含 `.env`、`*.pem` 及其他本地私钥/凭证文件；
   - 核查代码是否通过环境变量读取密钥（如 `os.environ["LLM_API_KEY"]`），严禁硬编码；
   - 核查仓库是否提供了不含真实值的 `.env.example` 占位模板（并在 `.gitleaks.toml` 合理放行纯占位符）。
5. **检查前端与构建产物**：浏览器端前端代码（如 `web/`、`frontend/`、`PUBLIC_` 变量）与构建产物中不得出现任何私有密钥，必须改由后端服务代理调用。

## 输出格式
- **结论**：通过 / 不通过
- **发现列表**：文件路径、行号、检测范围（工作区 / Git 历史）、密钥类型、脱敏片段（**只显示前 4 位，其余一律用 `*` 遮盖**，例如 `FAKE********`）
- **修复建议**：针对每项风险逐条列出具体可执行修复动作

## 发现泄露时的处置顺序
1. **第一优先级（立即止损）**：立即提醒用户前往对应服务商控制台**吊销并轮换该密钥**（删除代码或删除 Git 提交均无法撤回已暴露的凭证）。
2. **安全存放新密钥**：轮换后的新密钥只允许写入本地未跟踪的 `.env` 文件或专用密钥管理器（Secret Manager）。
3. **清理历史与审计账单**：按 GitHub 官方文档（如 `git filter-repo`）清理仓库历史记录，并核查密钥暴露期间的调用日志、用量与异常账单。
4. **加固长效防线**：开启代码托管平台的推送保护（Push Protection），并在本地配置 `pre-commit` 钩子接入 `gitleaks` 实现提交前硬阻断。

## 禁止事项
- **严禁二次泄露**：绝对不要在对话回复、终端日志或检查报告中输出完整密钥原文。
- **严禁擅自改写历史**：未经用户明确确认，绝对不要自动执行 `git push --force`、强制变基或改写 Git 历史等不可逆操作。
