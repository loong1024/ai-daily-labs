## 一、双盲架构评估提示词模板

```text
你是一位崇尚“简单优先（Single-First）”原则的首席 AI 系统架构师。请针对下方项目需求执行无偏见的双盲架构取舍评审，严禁默认推荐多智能体拆分：

【待评估项目输入】：{project_brief}
【SLO 与预算红线】：{slo_and_budget}

请严格按以下五步输出架构决策报告：
1. 耦合度与隐含决策审计：先检查各子产物之间是否存在 Cognition 所指出的“强共享上下文（Shared Context）”与“行动隐含设计决策（Actions Carry Implicit Decisions）”；再识别哪些部分属于 Anthropic 复盘中适合并行展开的“广度优先独立探索”。
2. 协议边界纠偏（MCP vs A2A & Handoff vs 按契约委派）：将确定性本地工具/数据读取归入 MCP；将跨组织边界、内部实现不透明且具备异步多轮状态（如 input-required）的黑盒智能体归入 A2A；明确区分控制权转移的 Handoff 与主控编排的按契约委派。
3. 绘制 A/B 双版对等草图：分别画出「A 版：单智能体串行闭环 + MCP 工具 + 按需外部 A2A」与「B 版：编排者 Orchestrator + 独立隔离工作区子智能体」，显式标出每一处的【共享状态】与【交接点/契约边界】。
4. 四维量化打分（1–5 分制）：围绕【子任务可解耦度】、【上下文共享紧密度】、【成本与延迟敏感度】、【调试排障复杂度】四个维度对 A、B 两版独立打分并测算 Token 倍率与 P95 延迟。
5. 拍板结论与演进阈值：给出当前阶段的唯一推荐方案，并写明当仓库规模、接口冻结程度或延迟预算发生何种量化变化时，才触发从 A 版切换至 B 版。
```

## 二、边界辨析：拆合原则、Handoff vs 契约委派、MCP vs A2A

- **何时适合并行拆分 vs 何时必须单兵串行**：
  - **适合多智能体并行拆分的 2 条核心依据（呼应 Anthropic 广度优先复盘）**：
    1. **子任务输入独立且只读无写冲突**：如面向几十个互不依赖的数据源、多语种技术文档或多个独立微服务仓做广度优先调研排查，子智能体各自搜索后只需向编排者返回高信噪比摘要，避免撑爆主上下文窗口；
    2. **接口契约已提前冻结且工作区物理隔离**：各子模块之间的函数签名、Schema 契约已在编码前完全锁死，且不同子智能体操作各自独立的沙箱目录/分支，不存在并发修改同一批文件的踩踏风险。
  - **必须保持单兵串行闭环的 2 条核心依据（呼应 Cognition 反面教训）**：
    1. **高度依赖完整共享上下文（Shared Context）**：本案例中单仓 PR 平均仅改 3–5 个文件，补丁修复、单测断言、CHANGELOG 三者紧密依赖同一份实时演进的代码细节，拆开会导致信息在摘要传递中失真；
    2. **每次行动都隐含设计决策（Actions Carry Implicit Decisions）**：修改代码补丁时顺手把返回值改为抛出 `OrderTimeoutError`，这一微观编码动作本身就决定了单测该怎么写异常断言、发布说明该怎么写兼容性提示——并行盲写必然产出互相矛盾的半成品。
- **交接（Handoff） vs 按契约委派（Contract Delegation）**：
  - **交接（Handoff）**：当前 Agent 将会话主导权与后续用户交互控制权直接移交给另一个专门角色（如客服一线路由转交人工或账单专员 Agent），原 Agent 退出主控回路。
  - **按契约委派（Contract Delegation）**：编排者（Orchestrator）始终持有全局状态与最终验收权，仅将边界清晰的子问题封装成明确的输入输出契约（Input/Output Contract）派发给子智能体或远程 A2A Agent，回收结构化结果并核验通过后再推进主流程。
- **MCP vs A2A 选型分界（彻底纠正初稿反模式）**：
  - **连本地确定性工具用 MCP（Model Context Protocol）**：初稿中把 `git diff`、`pytest`、`read_file` 包装成远程 A2A Agent 纯属过度设计。这些属于确定性、无自主规划意图的函数与资源，应直接通过本地 **MCP Server**（或原生 Tool）挂载给核心研发 Agent，微秒级调用且零额外模型推理税。
  - **跨组织不透明黑盒协办用 A2A（Agent2Agent Protocol）**：法务安全部的「开源许可证与出口管制合规智能体」拥有独立演进的私有判例库、专属推理策略与安全合规红线，对研发侧必须保持**内部实现不透明（Opaque）**——研发 Agent 无需也不被允许读取其底层 SQL 库，只需通过 **A2A** 提交依赖变更清单并订阅任务状态（`submitted` → `working` → `completed` / `failed`）。当遇到双许可证组件无法自动判定分发形态时，远程法务 Agent 会将任务置于 **`input-required`（需要补充输入）** 状态，附带结构化追问（如“请确认该依赖仅用于 CI 构建还是随容器镜像对外交付”），研发侧补充上下文后再恢复执行闭环。

## 四、四维量化评分表（1–5 分制）与架构改选阈值

> 评分口径说明：采用 `1–5` 分制量化对比两版方案在**当前每周 120 个单仓常规 PR（P95 ≤ 35s，单次成本 ≤ $0.08）**场景下的适配表现（5 分代表该维度对对应方案最有利/表现最佳，1 分代表风险或代价极高）。

| 评估维度 | A 版（单兵闭环，1-5 分） | B 版（多智能体，1-5 分） | 量化打分依据与工程测算 |
| :--- | :---: | :---: | :--- |
| 子任务可解耦度 | 5 | 2 | 当前 85% 常规单仓 PR 的补丁、单测、CHANGELOG 强绑定在同一函数签名变更上，天然不可拆（A 版契合度 5 分；强上 B 版可解耦度仅 2 分，仅外部法务合规可解耦）。 |
| 上下文共享紧密度 | 5 | 1 | 3–5 个文件的 Diff（约 4k Tokens）放入单窗口零损耗 100% 共享（A 版 5 分）；拆成多 Agent 会丢失隐含编码决策或被迫重复广播全量上下文（B 版 1 分）。 |
| 成本与延迟敏感度 | 5 | 2 | A 版单次约 $0.05、P95 约 22 秒，完全满足 ≤ $0.08 与 ≤ 35s 红线（5 分）；B 版多轮编排实测 Token 放大 4–6 倍（~$0.28–$0.49）、耗时 > 90s 超标（2 分）。 |
| 调试排障复杂度 | 5 | 2 | A 版仅 1 条线性工具调用轨迹 + 15% 场景一条外部 A2A Trace ID，分钟级定位（5 分）；B 版需交叉比对编排者与多个子工作区日志，排障成本陡增（2 分）。 |

- **明确选型结论**：
  - 当前阶段 **坚定选型「A 版：单智能体串行闭环 + 本地 MCP 工具集 + 跨部门法务 A2A 按契约协办」**（综合得分 20/20 vs B 版 7/20），彻底废弃初稿中把同仓改码、单测、文档强拆并发以及拿 A2A 包装本地 CLI 的反模式。
- **触发从 A 版改选 B 版的量化阈值条件**：
  - 仅当后续业务形态同时满足以下 **3 项量化演进阈值** 时，才针对特定大型任务启用 B 版（编排者 + 物理隔离 `git worktree` 子智能体）：
    1. **跨仓解耦规模阈值**：单次变更涉及 **≥ 5 个独立微服务仓库**（例如全集团统一的鉴权 SDK 升级或批量 CVE 漏洞修复），且各仓之间 Protobuf/OpenAPI 接口契约已提前冻结，子仓修改互不共享可变文件；
    2. **上下文容量阈值**：单次任务需同时检索与阅读的有效代码上下文持续超过 **80,000 Tokens**，导致单智能体窗口注意力明显退化；
    3. **SLO 与预算放宽阈值**：该类批处理升级任务允许异步执行（端到端延迟容忍度放宽至 **≥ 5 分钟**），且单任务模型预算上限放宽至 **≥ $0.50**（可承受 4–6 倍多智能体协调税）。
