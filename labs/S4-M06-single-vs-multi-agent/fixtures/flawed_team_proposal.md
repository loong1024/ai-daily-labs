# 待评审立项初稿：研发效能团队「PR 变更自动审查与开源合规放行系统」

## 1. 真实业务背景与约束
- **日常业务量**：核心交易后端单仓（Monorepo 单服务仓）每周约 **120 个常规 PR**，平均每个 PR 修改 **3–5 个源文件**（约 180 行 Diff）。
- **核心交付要求**：针对每个 PR，系统需产出三项强关联产物：
  1. **代码缺陷修复补丁建议**（可能会调整内部辅助函数的参数签名或返回错误码枚举）；
  2. **配套单元测试补充代码**（断言必须与第 1 项调整后的函数签名、异常类型及边界返回码 100% 吻合）；
  3. **面向测试与运维的变更说明（CHANGELOG 摘要）**（必须准确描述本次实际落地的接口行为与配置变化）。
- **跨部门合规协办要求**：当且仅当 PR 修改了依赖清单（如 `pyproject.toml` / `package.json`，约占全部 PR 的 15%）时，必须提请 **集团法务安全部独立维护的「开源许可证与出口管制合规智能体」** 审查。法务部出于合规审计保密要求，**绝不向研发部门开放其内部商业判例库源码与底层 SQL 权限**，有时在遇到双许可证（Dual-License）组件时还会中途挂起要求研发补充“该组件仅用于内部构建还是随镜像分发”的说明。
- **SLO 与成本预算**：研发团队要求常规 PR 反馈 P95 延迟 **≤ 35 秒**，单次 PR 自动化审查综合模型成本控制在 **≤ $0.08**。

## 2. 某架构师提交的初版「跟风全员多 Agent」方案（含 3 处严重反模式）

> **初版提案摘要（待你在实验中纠偏）**：
> 1. **无契约强拆同仓并发写**：为了显得架构先进，把每个单仓 PR 强行拆给 `Patch-Agent`（改代码）、`Test-Agent`（写单测）、`Doc-Agent`（写变更说明）三个智能体**同时在同一本地工作目录并发执行**，互不通气以追求“极致并行”。
>    - *试运行翻车实录*：`Patch-Agent` 将 `parse_order()` 的超时报错改成了 `OrderTimeoutError`，并发运行的 `Test-Agent` 仍按旧版返回 `None` 编写断言，且两者同时写同一个文件引发覆盖冲突，合并通过率仅 28%。
> 2. **MCP 与 A2A 协议彻底反配**：
>    - 给本地确定性的 `git diff`、`pytest`、`read_file` 每个命令各部署了一套带独立 System Prompt 的远程 HTTP A2A Agent 服务；
>    - 反过来要求法务安全部把内部开源判例数据库表直接通过本地 SQL 工具暴露给研发 Agent 查询，当场被安全团队驳回。
> 3. **忽视上下文碎片化与成本倍增**：4 个子 Agent 加 3 个伪工具 Agent 反复传递完整仓库文件树，单次 PR Token 消耗暴涨 **6.4 倍**（达 $0.49/PR），端到端 P95 耗时恶化至 **142 秒**，一处断言报错需要翻查 7 份交叉对话日志才能定位。
